# How NRE config parsing works

## NRE config parsing order

For parsing config files we use three libraries in the following order:

1. `hydra` resolves references/imports in `.yaml` files allowing us to split large configs into
   multiple files and add commandline overrides. It generates what is effectively a singLe large `.yaml`.

2. `omegaconf` parses the resulting `.yaml` into a `DictConfig`: an untyped nested structure. `DictConfig`
   is effectively a nested dict which supports the `config.attribute` syntax. `omegaconf` also resolves
   special expressions like `${eval:'0.0001 if "${model.bilateral_grid.name}"!="skip-bilateral-grid" else 0.0'}`.

3. `pydantic` is used to convert the untyped config produced by `omegaconf` into a strongly typed
   hierarchical structure with well-defined schema.

## Pydantic

Pydantic is a library which exposes functionality similar to python's dataclasses with an addition:
the type hints are used to auto-generate code which _verifies_ if the input arguments are of correct
type at runtime (PydanticBaseModel.model_validate) and other minor extras such as generating full
JOSN schemas.

## Usage in NRE

In `nre.config.base_schema` we expose `BaseConfigSchema` which is to be used as the base class of all config structs. It
behaves similar to python's `dataclass` i.e. autogenerates an `__init__` which all fields and defaults. We additionally
use two advanced features: [literals](https://docs.pydantic.dev/1.10/usage/types/#literal-type) and
[discriminated unions](https://docs.pydantic.dev/latest/concepts/unions/#discriminated-unions).

```
class SubconfigA(BaseConfigSchema):
    name: Literal["subconfig-a"] # used for discriminated unions

    val1: str

class SubconfigB(BaseConfig):
    name: Literal["subconfig-b"] # used for discriminated unions

    val2: int

class MainConfig(BaseConfig):
    regular_str_field: str
    literal_field: Literal["train", "validate"]
    nested_struct_field: SubconfigA
    discriminated_union_field: SubconfigA | SubconfigB = Field(discriminator="name")
    free_form_field: Any
```

### Regular fields

As expected, a field declared as `regular_str_field: str` will validate/convert the input to `str`.

### Literal fields

A field declared as `literal_field: Literal["train", "validate"]` will validate that the input is either
"train" or "validate" and error out on any other value. These options will be reflected in autogenerated docs.

### Nested struct fields

A field declared as `nested_struct_field: SubconfigA` will cause the parser to recurse and apply rules of `SubconfigA`
to parse and validate `nested_struct_field`.

### Discriminated unions

A field declared as `discriminated_union_field: SubconfigA | SubconfigB = Field(discriminator="name")` will recurse
and allow either `SubconfigA` or `SubconfigB` to be created. To remove the ambiguity which, it will check the input
for the field `name` (provided as the `discriminator` kwarg) and compare it to the type of that field in both
allowed structs. This is an unusual application of `Literal` as usually a `Literal` with a single choice offers
little value. This mechanism is used in NRE to handle user choices between model or dataset types.

### Free-form fields (`Any`)

Fields annotated as `typing.Any` remain effectively untyped, allowing for gradual adoption of strongly typed config.
`Any` can in particular hold nested sub-configs.
